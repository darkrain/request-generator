# Процесс Работы Со Спецификациями

Этот документ описывает общий порядок создания, изменения, принятия и устаревания спецификаций request-generator.

Сама исполняемая спецификация универсального рендера находится отдельно: [universal-renderer-contract.md](universal-renderer-contract.md).

Общие цели для всех спецификаций описаны отдельно: [specification-goals.md](specification-goals.md).

## Паспорт Спецификации

Каждая спецификация должна начинаться с паспорта:

- `Имя` - стабильное имя спецификации, например `UniversalRenderer`;
- `Версия` - версия конкретного контракта в формате semver, например `1.0.0`;
- `Статус` - текущий статус документа;
- `Владелец` - команда или мейнтейнеры, отвечающие за ревью и развитие.

Имя и версия должны быть отдельными значениями. Имя схемы и имя спецификации не разделяются: используется одно поле `Name`.

## Статусы

Каждый документ спецификации должен объявлять статус. Статус является частью метаданных спецификации и не должен опускаться.

Допустимые статусы:

| Статус | Значение |
|--------|----------|
| `draft` | Черновик. Можно реализовывать экспериментально, но несовместимые изменения еще разрешены. |
| `proposed` | Готово к ревью. Реализации не должны считать контракт стабильным. |
| `accepted` | Стабильный контракт, принятый мейнтейнерами. Действуют правила обратной совместимости. |
| `deprecated` | Документируется для существующих реализаций, но новые модули не должны его использовать. |
| `rejected` | Хранится только как исторический контекст. Не должен реализовываться. |

## Предложение Спецификации

Любой участник может предложить новую спецификацию или изменение существующей через pull request.

Предложение должно содержать:

- файл спецификации в `docs/`;
- `Name`;
- `Version`;
- `Status`;
- владельца или мейнтейнеров, ответственных за ревью;
- описание проблемы;
- заметки о совместимости;
- миграционные заметки, если меняется существующее поведение;
- минимум один реалистичный пример модуля;
- ответственность frontend и backend;
- требования безопасности.

Альтернативные спецификации должны использовать другое `Name` или major `Version`. Нельзя переиспользовать `Name: UniversalRenderer` с `Version: 1.0.0` для несовместимого поведения.

Примеры:

- `Name: UniversalRenderer`, `Version: 2.3.0`
- `Name: MobileRenderer`, `Version: 1.0.0`
- `Name: DashboardRenderer`, `Version: 1.0.0`

## Принятие Спецификации

Спецификация может перейти из `draft` или `proposed` в `accepted` только после того, как:

- минимум один backend-модуль реализует ее;
- минимум один frontend-рендер использует ее;
- мейнтейнеры проверят совместимость и требования безопасности;
- PR опишет влияние на существующие модули.

После принятия несовместимые изменения требуют новой версии для того же имени или нового имени, если контракт описывает другое семейство рендеров.

## Правила Совместимости

Обратно совместимые изменения:

- добавление optional fields;
- добавление новых renderer names;
- добавление новых field flow types;
- добавление optional response metadata.

Несовместимые изменения:

- изменение CRUD route mapping;
- изменение required keys;
- изменение error shape;
- изменение семантики существующего renderer или field flow type.

Несовместимые изменения требуют новой версии для того же имени спецификации.
